# 24장. 디버그 뷰, 테스트, 프로파일링

> _렌더러는 이미지가 맞는지만 보는 프로그램이 아니다. 각 단계가 만든 수치와 불변조건을 자동으로 설명할 수 있어야 한다._

> **이번 장의 눈에 보이는 결과**  네이티브 단위 테스트, 작은 golden image, 브라우저 smoke test, debug view, p50/p95 성능 표가 한 명령 흐름으로 실행된다.

## 왜 필요한가

그래픽 오류는 마지막 화면에서 멀리 떨어진 원인 때문에 생긴다. 검은 화면 하나로는 clip에서 모두 사라졌는지, culling 부호가 반대인지, depth가 NaN인지 알 수 없다. 단계별 통계와 특화 debug view가 원인 탐색 시간을 크게 줄인다.

최적화 전에 기준 이미지와 측정 방법을 고정하지 않으면 빨라졌지만 틀린 결과를 받아들일 수 있다. scalar reference와 작은 결정적 scene을 보존한 뒤 release Wasm에서 시간을 잰다.

## 배경지식

- <strong>단위 테스트</strong>: Vec/Mat, clip distance/intersection, edge/top-left, barycentric, depth, sampler, color transfer처럼 순수 함수를 네이티브에서 검사한다.
- 좌표 fixture는 `look_at_lh` 기저, `perspective_lh_zo`의 `+near/+far`, `w_clip=z_view`, 큐브 normal/winding/culling과 glTF basis conversion을 포함한다.
- <strong>property/invariant 테스트</strong>: barycentric 합, clip 후 여섯 plane 내부, quad owner=1, opaque draw-order independence처럼 많은 입력에 성립할 관계를 검사한다.
- <strong>golden image</strong>: 32x32 또는 64x64의 결정적 scene RGBA를 파일/hash로 비교한다. 큰 screenshot 하나보다 작은 fixture 여러 개가 원인 분리에 좋다.
- <strong>브라우저 통합</strong>: Wasm 초기화, memory view, resize, input focus, ImageData 표시를 headless browser로 검사한다.
- <strong>성능 측정</strong>: debug가 아닌 release, warm-up 뒤 동일 scene/해상도에서 frame time ring buffer의 p50/p95를 기록한다.

## 핵심 식과 불변조건

```text
opaque invariant: render(order A).rgba == render(reverse(order A)).rgba
coverage invariant for quad: owner_count[p] in {0,1}, and intended interior is exactly 1
stats relation: shaded <= depth_pass <= covered_samples
frame report tuple: build mode, browser, device, resolution, triangles, samples, p50 ms, p95 ms
```

## 알고리즘과 구현 순서

1. debug modes를 Unlit, Wireframe, TriangleId, Barycentric, Depth, Normal, UV, NdotL, MipLevel, Overdraw로 정리한다.
1. 각 알고리즘 모듈에 작은 fixture와 기대 수치를 만든다. random property test를 쓰더라도 seed를 기록한다.
1. golden scene은 외부 asset에 의존하지 않는 triangle/quad/cube로 만들고 RGBA와 depth hash를 저장한다.
1. 브라우저 smoke test는 init -&gt; frame -&gt; Canvas nonempty -&gt; resize -&gt; frame -&gt; input을 검사하고 console error를 실패로 취급한다.
1. JS가 total render/present 시간을 ring buffer에 모아 warm-up 이후 p50/p95를 계산한다. Rust stats의 counts와 함께 JSON 또는 표로 저장한다.

```text
test ladder:
  cargo test renderer-core
  build wasm release
  run deterministic wasm/browser tests
  render golden scenes at fixed size and seed
  compare exact pixels or documented tolerance
  run benchmark scene after warm-up
  report p50/p95 with counts and environment

black screen triage:
  check frame/view -> stats -> clip -> cull -> coverage
  -> depth -> shader -> present, in that order
```

## JS-Wasm 경계

core 알고리즘 테스트는 브라우저 없이 실행한다. 브라우저 테스트는 JS-Wasm 경계와 실제 Canvas를 검증한다. JS는 timing과 환경 메타데이터를 수집할 수 있고 Rust는 단계별 count를 제공한다. 내부 픽셀 데이터를 디버깅할 때도 임시 API를 제품 공개 API로 굳히지 않는다.

## 코딩 에이전트 작업 명세

- 각 장에서 만든 테스트를 unit/property/golden/browser 네 층으로 분류하고 한 실행 문서로 연결한다.
- debug mode enum과 FrameStats를 UI overlay에 연결하고 impossible relation을 assertion으로 만든다.
- release benchmark scene, warm-up 프레임 수, 샘플 수, p50/p95 계산을 자동화한다.
- 성능 변경 PR에는 기준/변경 이미지 hash와 동일 환경 전후 수치를 요구하는 체크리스트를 만든다.

## 검증 기준

- 모든 core 테스트가 native에서 통과하고 wasm build가 별도로 통과해야 한다.
- golden 실패가 몇 픽셀/어느 위치/최대 채널 차이인지 보고해야 한다.
- browser test가 stale memory view와 resize regression을 재현해 잡을 수 있어야 한다.
- debug view를 바꿔도 geometry/depth counts가 의도 없이 변하지 않아야 한다.
- benchmark 보고서에 debug/release, 해상도, sample 수가 빠지면 성능 비교를 무효로 처리한다.

### 자주 생기는 오류

- screenshot만 눈으로 비교하면 한 픽셀 균열이나 색 공간 차이를 놓친다. pixel diff와 수치 테스트를 함께 쓴다.
- 첫 몇 프레임의 Wasm/JIT/asset 준비 시간을 steady-state와 섞지 않는다. warm-up을 분리한다.
- 평균 FPS 하나는 hitch를 숨긴다. p50/p95 frame ms와 stage count를 기록한다.
