# 1장. 소프트웨어 래스터라이저가 하는 일

> _목표는 GPU를 흉내 내는 것이 아니라, 삼각형이 어떤 규칙으로 픽셀이 되는지 한 단계씩 관찰 가능한 프로그램으로 만드는 것이다._

> **이번 장의 눈에 보이는 결과**  고정 색으로 화면을 지우고, 프레임마다 색이 천천히 변하는 Canvas를 표시한다. WebGL과 WebGPU 호출은 없어야 한다.

## 왜 필요한가

래스터라이저를 처음 만들 때 가장 흔한 실패는 행렬부터 코딩하는 것이다. 화면에 아무것도 나오지 않으면 변환, 클리핑, 삼각형 포함 검사, 색 쓰기 중 어디가 틀렸는지 알 수 없다. 먼저 한 프레임이 어떤 데이터 흐름을 거치는지 정하고, 각 단계가 관찰 가능하도록 만든다.

래스터화는 연속적인 기하 도형을 이산적인 픽셀 샘플로 바꾸는 과정이다. 삼각형 내부의 모든 점을 칠하는 것이 아니라, 각 픽셀을 대표하는 샘플 위치가 삼각형에 포함되는지를 결정한다. 이 관점이 뒤의 edge 함수, top-left 규칙, MSAA까지 그대로 이어진다.

## 배경지식

- <strong>래스터화와 레이 트레이싱의 차이</strong>: 이 과정은 각 삼각형이 어떤 픽셀을 덮는지 찾는다. 각 픽셀에서 광선을 쏘아 물체와 교차시키는 레이 트레이싱 과정이 아니다.
- <strong>정점 단계와 픽셀 단계</strong>: 정점 단계는 모델의 몇 천 또는 몇 만 정점을 좌표 변환한다. 래스터 단계는 삼각형이 덮는 훨씬 많은 픽셀 샘플을 검사한다. 최적화 지점도 서로 다르다.
- <strong>색 버퍼와 깊이 버퍼</strong>: 색 버퍼는 최종 RGBA를, 깊이 버퍼는 현재 픽셀에서 가장 가까운 표면의 깊이를 저장한다. 둘은 같은 x, y 인덱스를 공유한다.
- <strong>프레임</strong>: 입력을 읽고, 장면 상태를 갱신하고, 버퍼를 지우고, 모든 삼각형을 그린 뒤, 완성된 색 버퍼를 Canvas에 표시한 한 주기다.

## 핵심 식과 불변조건

```text
최종 데이터 흐름: mesh -> transform -> clip -> divide -> viewport -> coverage -> interpolate -> depth -> shade -> RGBA
픽셀 인덱스: pixel_index = y * width + x,  byte_index = 4 * pixel_index
```

## 알고리즘과 구현 순서

1. Renderer가 소유할 최소 상태를 정한다: width, height, RGBA8 색 버퍼, f32 깊이 버퍼, 장면/카메라, 프레임 통계.
1. 프레임 시작에서 색 버퍼를 배경색으로 채운다. 아직 삼각형은 그리지 않는다.
1. 프레임 번호나 시간으로 배경색을 조금씩 바꾼다. 이 변화가 보이면 rAF, JS-Wasm 호출, 메모리 뷰, Canvas 표시 경로가 모두 연결된 것이다.
1. render 단계별 통계를 0으로 초기화하고 프레임 끝에 반환한다. 다음 장부터 입력 정점 수, 클리핑된 삼각형 수, 통과 픽셀 수를 추가한다.

```text
frame(dt, input):
  update_scene(dt, input)
  clear_color(background_rgba)
  clear_depth(1.0)
  reset_stats()
  # later chapters insert draw_meshes() here
  return framebuffer_range_and_stats
```

## JS-Wasm 경계

JS는 브라우저의 다음 repaint 직전에 프레임을 요청하고, Wasm의 고수준 프레임 함수를 한 번 호출한다. Wasm은 색 버퍼의 주소와 길이만 노출한다. JS가 픽셀마다 Rust 함수를 호출하거나 Rust가 DOM 요소를 직접 만지는 구조는 이 과정의 기본 경로에서 제외한다.

## 코딩 에이전트 작업 명세

- workspace에 renderer-core, renderer-wasm, web의 최소 골격을 만들되 그래픽 API 의존성은 추가하지 않는다.
- Renderer의 생성, clear, resize, frame 통계 구조만 구현한다. 아직 벡터/행렬/mesh 코드는 넣지 않는다.
- 개발 빌드와 release Wasm 빌드를 각각 수행하는 명령을 문서화한다. 버전 번호는 현재 저장소 도구가 결정하도록 하고 교재에 고정하지 않는다.
- 브라우저에서 Canvas가 변하는 최소 통합 검사를 만들고, 네이티브 Rust에서는 buffer 길이와 clear 결과를 단위 테스트한다.

## 검증 기준

- width=3, height=2이면 색 버퍼 길이는 24바이트이고 깊이 버퍼 길이는 6이어야 한다.
- clear 뒤 모든 alpha 바이트는 255이고, 지정한 RGB가 모든 픽셀에 반복되어야 한다.
- Canvas의 CSS 크기와 내부 해상도를 화면에 표시해 둘이 구분되는지 확인한다.
- 브라우저 개발자 도구에서 WebGL/WebGPU context가 생성되지 않았음을 확인한다.

### 자주 생기는 오류

- Canvas가 검은 화면일 때 수학 문제라고 단정하지 않는다. 이 장에서는 Wasm 초기화, 버퍼 길이, ImageData 크기, alpha 값을 먼저 확인한다.
- 프레임마다 Renderer나 Vec을 새로 만들면 이후 성능 분석이 왜곡된다. 생성과 프레임 실행을 분리한다.
- rAF 횟수를 고정 60Hz로 가정하면 고주사율 모니터에서 움직임이 빨라진다. 전달된 timestamp로 dt를 계산한다.
