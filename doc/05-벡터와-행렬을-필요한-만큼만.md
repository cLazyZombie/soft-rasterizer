# 5장. 벡터와 행렬을 필요한 만큼만

> _선형대수 전체를 배우지 않는다. 위치, 방향, 좌표계 변환, 면의 방향을 표현하는 연산만 정확히 익힌다._

> **이번 장의 눈에 보이는 결과**  단위 테스트로 검증된 Vec2/Vec3/Vec4/Mat4가 있고, 축과 법선 debug 선이 예상 방향으로 보인다.

## 왜 필요한가

그래픽스 오류의 상당수는 어려운 수학보다 규약 혼합에서 생긴다. 행렬을 행 우선으로 저장하면서 열벡터 식을 쓰거나, 점과 방향을 모두 w=1로 다루거나, normalize(0)를 허용하면 뒤 단계가 무너진다.

직접 만든 작은 수학 타입은 교육적으로 유리하다. 어떤 연산이 왜 필요한지 보이고, 좌표 규약을 테스트로 고정할 수 있다. 최종 제품에서 검증된 수학 라이브러리로 바꾸더라도 이 규약 문서는 유지해야 한다.

## 배경지식

- <strong>점과 방향</strong>: 동차좌표에서 점은 (x, y, z, 1), 방향은 (x, y, z, 0)이다. 이동 행렬은 점에는 영향을 주고 방향에는 영향을 주지 않는다.
- <strong>dot(a, b)</strong>는 두 방향의 정렬 정도다. 단위 벡터라면 1은 같은 방향, 0은 직각, -1은 반대다.
- <strong>cross(a, b)</strong>는 두 벡터에 수직인 방향을 만든다. 정점 순서로부터 면 법선을 얻고 backface를 판단할 때 쓴다.
- 이 교재는 통상적인 algebraic cross 식과 `cross(X,Y)=Z`를 유지한다. 좌표계의 handedness 때문에 cross 결과를 임의로 음수화하지 않는다. 왼손 카메라 기저는 7장에서 cross의 <strong>인자 순서</strong>로 만든다.
- <strong>normalize(v)</strong>는 길이를 1로 만든다. 길이가 거의 0이면 나누지 말고 실패 또는 기본값을 반환한다.
- <strong>Mat4 규약</strong>: 이 교재는 열벡터를 사용하고 p_clip = P \* V \* M \* p_object 순서를 고정한다. 메모리 저장 순서는 별개지만 인덱싱 함수가 숨겨야 한다.

## 핵심 식과 불변조건

```text
dot(a, b) = ax*bx + ay*by + az*bz
length(v) = sqrt(dot(v, v)),  normalize(v) = v / length(v)
cross(a,b) = (ay*bz-az*by, az*bx-ax*bz, ax*by-ay*bx)
회전 기준: Rx(+π/2)*Y=Z, Ry(+π/2)*Z=X, Rz(+π/2)*X=Y
변환 합성: p_world = M * p_object, p_view = V * p_world, p_clip = P * p_view
```

## 알고리즘과 구현 순서

1. Vec 타입에 add, sub, scalar mul/div, dot, length, normalize를 구현한다. Vec3에는 cross를 추가한다.
1. Mat4 identity, translation, scale, rotation_x/y/z, matrix-matrix, matrix-vector 곱을 구현한다.
1. 행렬의 논리적 row, col 접근 함수를 만들고 저장 순서를 외부 코드가 직접 가정하지 못하게 한다.
1. 부동소수점 테스트는 정확한 == 대신 abs(actual-expected) &lt;= epsilon을 사용한다. 단, identity의 정수 성분처럼 정확해야 하는 값은 별도 검사할 수 있다.
1. 축 debug draw를 위해 원점에서 +X 빨강, +Y 초록, +Z 파랑 선을 만들고 이후 카메라를 붙였을 때 방향을 확인한다.

```text
normalize_or_none(v):
  len2 = dot(v, v)
  if len2 <= EPSILON * EPSILON:
    return None
  return v / sqrt(len2)

transform_point(M, p):
  return M * Vec4(p.x, p.y, p.z, 1)

transform_direction(M, d):
  return M * Vec4(d.x, d.y, d.z, 0)
```

## JS-Wasm 경계

수학 타입은 전부 renderer-core에 있고 JS 배열 타입과 결합하지 않는다. 카메라 입력처럼 JS에서 넘어오는 값은 adapter에서 core Vec로 한 번 변환한다. Mat4 전체를 매 프레임 JS에서 만들어 넘기지 않고, 카메라 파라미터를 Rust가 행렬로 구성하는 경로를 기본으로 한다.

## 코딩 에이전트 작업 명세

- 외부 수학 crate 없이 최소 타입을 먼저 구현한다. 이미 저장소에 수학 라이브러리가 있다면 직접 구현 대신 동일 규약을 감싼 adapter와 규약 테스트를 만든다.
- 열벡터, 왼손 좌표계, `+X` 오른쪽, `+Y` 위, 카메라 전방 `+Z`, 화면 y-down이라는 결정을 docs/decisions/coordinates.md에 기록한다.
- 각 생성 행렬과 합성 순서의 테스트를 작성한다. 회전 테스트는 90도 축 회전처럼 기대값이 분명한 사례를 쓴다.
- normalize zero 처리와 NaN 전파 방지 정책을 문서화한다.

## 검증 기준

- identity \* v = v, translation은 point만 이동하고 direction은 이동하지 않아야 한다.
- scale 뒤 translation과 translation 뒤 scale이 다르다는 테스트로 곱 순서를 고정한다.
- cross(X, Y)=Z이고 dot(X, Y)=0이어야 한다. winding 규약과 맞는지도 9장에서 다시 확인한다.
- `rotation_x(+π/2)*Y=Z`, `rotation_y(+π/2)*Z=X`, `rotation_z(+π/2)*X=Y`로 양의 회전 의미를 고정한다.
- 0벡터 normalize가 NaN을 만들지 않고 명시된 실패 경로를 탄다.

### 자주 생기는 오류

- 행렬 저장 순서와 수학적 곱 순서를 같은 개념으로 취급하지 않는다. get(row,col)와 mul 구현을 테스트로 봉인한다.
- degree를 radian으로 바꾸지 않고 sin/cos에 넣으면 카메라가 이상하게 움직인다.
- f32 오차를 숨기려고 epsilon을 지나치게 크게 잡으면 실제 오류도 통과한다. 연산 규모에 맞는 작은 epsilon을 사용한다.
