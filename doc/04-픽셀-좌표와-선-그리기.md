# 4장. 픽셀 좌표와 선 그리기

> _선은 최종 렌더링의 주인공이 아니지만, wireframe, bounding box, 법선 방향을 보여 주는 가장 중요한 디버그 도구다._

> **이번 장의 눈에 보이는 결과**  Canvas 위에 격자, 임의 기울기의 선, 삼각형 wireframe이 끊김 없이 보이고 화면 밖으로 나간 선도 안전하게 처리된다.

## 왜 필요한가

3D 파이프라인에서 색칠된 삼각형이 보이지 않을 때 정점의 화면 좌표를 선으로 연결하면 변환 문제인지 래스터 문제인지 분리할 수 있다. 선 알고리즘은 좌표가 실수에서 정수 샘플로 바뀌는 첫 경험이기도 하다.

DDA는 식이 단순해 이해하기 좋고, Bresenham은 정수 누적 오차로 같은 일을 수행해 증분 알고리즘의 감각을 준다. 이 저장소의 4장 구현은 학습자 선택에 따라 DDA를 구현 경로로 두지 않고 all-octants Bresenham을 기본이자 유일한 선 래스터화 경로로 사용한다. 11장의 edge 함수도 매 픽셀마다 식을 새로 계산하지 않고 차이를 누적한다는 점에서 같은 생각을 사용한다.

## 배경지식

- <strong>화면 좌표</strong>는 왼쪽 위가 (0, 0), x는 오른쪽, y는 아래로 증가한다고 고정한다.
- <strong>픽셀의 셀과 샘플</strong>을 구분한다. 픽셀 (x, y)의 영역은 대략 [x, x+1) x [y, y+1)이고 대표 샘플은 (x+0.5, y+0.5)다.
- <strong>DDA</strong>는 긴 축의 길이만큼 t를 증가시키고 x, y를 선형 보간한 뒤 가장 가까운 픽셀을 선택한다.
- <strong>Bresenham</strong>은 실제 선과 선택한 픽셀 중심 사이의 오차를 정수로 누적해 다음 x 또는 y 이동을 결정한다.
- <strong>클리핑</strong>: 교육용 put_pixel이 경계를 확인하면 안전하지만 긴 화면 밖 선은 낭비가 크다. Cohen-Sutherland나 Liang-Barsky 선 클리핑은 선택 확장이다.

## 핵심 식과 불변조건

```text
dx = abs(x1 - x0), sx = x0 < x1 ? 1 : -1
dy = -abs(y1 - y0), sy = y0 < y1 ? 1 : -1
error = dx + dy
e2 = 2 * error
e2 >= dy이면 error += dy, x0 += sx
e2 <= dx이면 error += dx, y0 += sy
```

## Bresenham 한 줄을 직접 계산하기

(0,0)에서 (4,2)까지 그리자. 이 장의 의사 코드처럼 `dx=4`, `dy=-2`, `sx=sy=1`, `error=dx+dy=2`로 시작한다.

```text
현재 픽셀    e2=2*error    다음 이동       이동 후 error
(0,0)       4             x와 y 둘 다    4
(1,1)       8             x만            2
(2,1)       4             x와 y 둘 다    4
(3,2)       8             x만            2
(4,2)       끝점이므로 종료
```

첫 반복에서 x 조건 `e2>=dy`가 참이므로 error에 dy=-2를 더해 0이 된다. y 조건도 **처음 계산한 e2=4**로 검사한다. `e2<=dx`도 참이므로 error에 dx=4를 더하고 y를 옮긴다. 따라서 두 조건은 `if/else`가 아닌 독립된 `if`여야 한다.

좌표 차이는 빼기 전에 넓힌다. `i64(x1)-i64(x0)`은 안전하지만 `i64(x1-x0)`은 i32 뺄셈에서 먼저 overflow할 수 있다. 범위를 검사하는 put_pixel은 메모리를 보호한다. 아주 긴 선의 반복 횟수를 줄이는 clipping과는 다른 책임이다.

## 알고리즘과 구현 순서

1. 좌표 차이는 i64로 확장한 뒤 `abs`를 적용해 i32 양 끝값에서도 overflow하지 않게 한다.
1. 현재 픽셀을 먼저 safe put_pixel에 전달하고, 시작점과 끝점이 같으면 한 픽셀을 쓴 뒤 종료한다.
1. 두 배 오차와 dx/dy를 비교해 x, y 또는 둘 다 한 칸 전진한다. 양 끝점을 모두 포함한다.
1. 수평, 수직, 45도, 완만/급한 양/음 기울기 선을 모두 그려 octant 누락이 없는지 확인한다.
1. triangle wireframe은 세 변을 같은 색 또는 변별 색으로 그린다. 정점 점도 별도 색으로 찍어 winding을 확인하게 한다.

```text
draw_line_bresenham(p0, p1, color):
  dx = abs(p1.x - p0.x); sx = sign(p1.x - p0.x)
  dy = -abs(p1.y - p0.y); sy = sign(p1.y - p0.y)
  error = dx + dy
  loop:
    put_pixel(p0.x, p0.y, color)
    if p0 == p1: break
    e2 = 2 * error
    if e2 >= dy: error += dy; p0.x += sx
    if e2 <= dx: error += dx; p0.y += sy
```

## JS-Wasm 경계

선 그리기는 Rust frame 안의 debug draw pass다. JS Canvas의 stroke나 lineTo를 쓰면 실제 Wasm 좌표 규약과 다른 렌더러를 보게 되므로, overlay 텍스트 외의 기하 디버그는 같은 프레임버퍼에 그린다.

## 코딩 에이전트 작업 명세

- 정수 화면 좌표와 Color를 최소 정의하고 all-octants Bresenham 선, 점, 사각형 outline, wireframe helper를 추가한다.
- safe put_pixel 경로를 사용해 화면 밖 좌표가 있어도 메모리 오류가 없게 한다.
- 모든 octant를 한 화면에 보여 주는 debug scene과 작은 예상 이미지 테스트를 만든다.
- DDA나 JS Canvas 선 경로를 병행하지 않고, 다음 장에서도 같은 Bresenham debug helper를 재사용한다.

## 검증 기준

- 같은 시작/끝점, 수평/수직, 양/음 기울기, 화면 경계 교차, 완전히 화면 밖인 선을 검사한다.
- 선의 두 끝점이 모두 포함되고, 연결된 wireframe 모서리에 한 픽셀짜리 틈이 없는지 확대 확인한다.
- 64x64 golden image를 픽셀 단위로 비교해 브라우저 확대 방식과 무관한 결과를 얻는다.
- 선 디버그를 끄면 렌더 통계의 debug pixel 수가 0으로 돌아가는지 확인한다.

### 자주 생기는 오류

- `i32::MIN`에 직접 `abs`를 적용하면 overflow할 수 있다. 차이를 i64로 확장한 뒤 절댓값을 구한다.
- 시작점과 끝점이 같은 경우를 끝점 검사보다 먼저 쓰지 않으면 퇴화 선의 유일한 픽셀이 빠진다.
- JS Canvas 선을 겹쳐 그리면 반 픽셀 정렬과 antialiasing 때문에 Rust 결과와 다르게 보여 디버깅을 오도한다.
