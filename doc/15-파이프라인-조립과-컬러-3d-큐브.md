# 15장. 파이프라인 조립과 컬러 3D 큐브

> _지금까지의 작은 함수를 순서대로 연결하되, 단계 사이의 타입과 통계를 유지해 검은 화면을 추적 가능하게 만든다._

> **이번 장의 눈에 보이는 결과**  회전하는 컬러 큐브가 클리핑, culling, top-left, barycentric, depth를 모두 거쳐 안정적으로 렌더링된다.

## 왜 필요한가

개별 알고리즘이 맞아도 순서가 틀리면 파이프라인은 깨진다. 특히 clipping 전 divide, culling 부호, depth 범위, framebuffer resize가 연결 지점에서 자주 충돌한다.

이 장의 목적은 추상적인 shader framework를 크게 설계하는 것이 아니다. VertexOutput, ScreenVertex, FragmentInput처럼 단계별 데이터 계약을 최소로 만들고, 각 단계 통계와 debug view로 실패 지점을 좁히는 것이다.

## 배경지식

- <strong>vertex stage</strong>는 index마다 한 번 clip vertex를 만든다.
- <strong>primitive stage</strong>는 triangle 조립, clipping, perspective divide, viewport, culling을 처리한다.
- <strong>raster stage</strong>는 triangle setup, coverage, barycentric, depth를 처리한다.
- <strong>fragment stage</strong>는 현재 장에서는 vertex color만 반환한다. 다음 부에서 texture와 lighting을 추가한다.
- <strong>pipeline state</strong>는 cull mode, depth test, debug mode, material을 포함하되 전역 mutable flag를 흩뿌리지 않는다.

## 핵심 식과 불변조건

```text
FrameStats: input_vertices, input_triangles, clipped_away, generated_triangles, culled, degenerate, covered_samples, depth_pass, shaded
불변 순서: transform -> clip -> divide -> viewport -> cull/setup -> coverage -> depth -> shade -> color write
```

## 알고리즘과 구현 순서

1. 프레임 시작에서 camera/scene을 갱신하고 color/depth를 clear한다.
1. mesh의 정점을 vertex stage로 변환해 ClipVertex 캐시를 만든다.
1. index triangle을 조립하고 clip polygon을 만든 뒤 fan triangles를 생성한다.
1. 각 생성 triangle을 divide/viewport하고 positive winding/culling/degenerate 검사를 통과시킨다.
1. triangle setup과 coverage loop에서 barycentric, depth test, perspective interpolants를 계산하고 fragment color를 쓴다.
1. 프레임 끝에 통계를 확정하고 JS가 overlay에 표시할 작은 스냅샷을 제공한다.

```text
render_frame(scene, camera):
  targets.clear(color=background, depth=INF)
  VP = projection(camera) * view(camera)

  for draw in scene.draw_items:
    transformed = vertex_stage(draw.mesh, VP * draw.model)
    for indexed_triangle in draw.mesh:
      polygon = clip_triangle(transformed[indices])
      for triangle in triangulate_fan(polygon):
        screen_tri = divide_viewport_cull(triangle)
        if screen_tri exists:
          rasterize(screen_tri, targets, material)

  return stats
```

## JS-Wasm 경계

JS 프레임 루프는 dt와 입력 스냅샷을 전달하고, 완성된 색 버퍼와 FrameStats만 읽는다. 각 파이프라인 단계를 JS에서 순서대로 호출하지 않는다. Rust의 한 render 호출 안에서 상태가 일관되게 유지되어야 한다.

## 현재 구현

- `Renderer::update_and_render` 한 번이 모델 회전 갱신, vertex cache 재구축, clip/fan, divide/viewport, culling/setup, coverage, affine `z_ndc` depth, perspective 속성 복원, fragment 색 기록을 순서대로 끝낸다. JS는 완성된 RGBA8와 작은 통계만 읽는다.
- 기본 큐브 카메라는 `eye=(0,0,-3)`, `target=(0,0,0)`, `world_up=(0,1,0)`, LH/+Z, 60도 FOV, near 0.1, far 100으로 고정했다. 모델의 Y 회전만 고정 `dt`로 갱신하므로 같은 pose와 입력은 같은 framebuffer를 만든다.
- `PipelineState`가 `CullMode`, `AttributeInterpolationMode`, `PipelineDebugMode`를 소유한다. material은 `DrawItem`이 소유하고 depth는 모든 모드에서 `+infinity` clear와 strict `<` test/write로 고정한다.
- `PipelineDebugMode`는 solid, wireframe, triangle ID, barycentric, depth grayscale/heatmap, front/back을 통합한다. Wireframe도 Canvas나 별도 line pass가 아니라 coverage를 통과한 fragment의 barycentric edge 거리를 색으로 표현한다. 따라서 모든 모드가 geometry, coverage와 depth 통계를 공유한다.
- 이전 장의 Bresenham X-ray 진단선은 통합 debug mode와 별개의 opt-in overlay로 남기고 기본값은 꺼 둔다. 따라서 기본 UI와 15장 golden은 가려진 edge를 depth 밖에서 덮어쓰지 않는다.
- `FrameStats`에 `covered_samples`와 `sample_counter_overflow`를 추가한다. 각 `u32` sample counter는 overflow 시 `u32::MAX`로 고정하고 flag를 세워 잘린 통계를 정상 관계식으로 오인하지 않으며, flag가 거짓일 때만 다음 관계를 debug assertion으로 확인한다.

```text
generated = submitted + culled + degenerate + invalid
rasterized = submitted
covered = depth_passed + depth_failed + invalid_depth + invalid_interpolation
shaded = depth_passed = interpolated_inv_w_samples
```

- source vertex transform cache와 `TriangleClipper`의 polygon/fan scratch capacity는 프레임 사이 재사용한다. triangle/fragment별 heap allocation이나 worker/SIMD 경로는 추가하지 않았다.
- native fixture는 outward normal과 screen front-face 일치, near plane을 가르는 가까운 카메라, culling off 상태의 역순 triangle 제출, 일곱 debug mode의 동일 depth/통계를 고정한다. Browser fixture는 960x540에서 같은 Rust-Wasm-Canvas 경로의 큐브와 각 debug mode pixel hash를 DPR 1x/2x에서 비교한다.

## 코딩 에이전트 작업 명세

- 기존 단계를 Pipeline 또는 Renderer 내부에서 명시적 순서로 조립하고 각 단계 함수의 입력/출력 타입을 다르게 둔다.
- solid, wireframe, triangle ID, barycentric, depth, front/back debug mode를 enum으로 통합한다.
- FrameStats를 매 프레임 초기화하고 관계식이 맞는지 debug assertion을 추가한다.
- 브라우저 smoke test에서 큐브가 일정 각도일 때 framebuffer hash 또는 screenshot을 비교한다.
- 기본 장면은 `eye=(0,0,-3)`, `target=(0,0,0)`, `world_up=(0,1,0)`인 LH/+Z 카메라처럼 재현 가능한 pose를 fixture에 기록한다.

## 검증 기준

- input triangles=12인 큐브에서 generated, clipped, culled, rasterized 수의 관계가 통계와 맞아야 한다.
- 기본 pose에서 outward normal, screen `orient2d&gt;0` front-face와 culling 결과가 일치해야 한다.
- 카메라가 큐브에 가까워 near plane을 통과해도 NaN, 전체 화면 폭발, 갑작스러운 전체 소실이 없어야 한다.
- culling을 끄고 triangle 순서를 뒤집어도 depth가 최종 가시 표면을 유지해야 한다.
- 각 debug mode가 동일한 coverage/depth 경로를 사용하고 색 표현만 바꾸는지 확인한다.
- release 빌드에서 프레임 hot path의 heap allocation 수가 정점/삼각형 수에 불필요하게 비례하지 않아야 한다.

### 자주 생기는 오류

- debug wireframe을 실제 fill 뒤 Canvas API로 그리면 좌표 규약이 갈라진다. 같은 Rust framebuffer에 그린다.
- clip 결과 Vec을 매 삼각형마다 새 allocation하면 성능이 빠르게 나빠진다. 작은 고정 용량 버퍼나 재사용 Vec을 고려하되 정확성 뒤에 최적화한다.
- 한 번에 texture, lighting, asset loader까지 넣지 않는다. 이 장의 컬러 큐브를 안정적인 회귀 기준으로 보존한다.
